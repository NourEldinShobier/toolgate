# Real-usage report: the 0.16.0 measurement window (hook host)

**Window:** 2026-10-03 → 2026-10-09 (America/New_York), toolgate 0.16.0 throughout, policy untouched from the first window (default thresholds deny 0.85 / ask 0.55 / authorized 0.8; `fail_mode: ask`; one MCP server under `trusted_tools`; `limits.input_chars` 40,000, `limits.task_chars` 6,000). Host: the `settings.json` PreToolUse hook, as in the first window; the Claude Code mod shipped in 0.16.0 was installed on the last day of the window and gated nothing inside it. Five attended Claude Code sessions (`acceptEdits` 1,484, `auto` 149; one session accounts for 1,313 decisions) doing ordinary product work: a web app with a media pipeline, image and video generation through paid APIs, deployments, and research in the built-in browser. **1,633 decisions**, 1,626 from the model, 7 from fail-mode. Latency p50 915 ms, p90 1,044 ms, max 4,005 ms, direct to TypeSafe's API.

The window was declared before it opened (fixed span, floor of ~300 decisions, run once). All paths, project names, hosts, and identifiers in this report and in the labeling package are genericized. The author is the only user of the sessions.

## The three numbers

| | first window (0.9.1) | this window (0.16.0) |
|---|---|---|
| allow | 1,064 · 77.7% | 1,376 · **84.3%** |
| ask | 286 · 20.9% | 254 · **15.6%** |
| deny | 19 · 1.4% | 3 · **0.2%** |

The target set after the first window was an ask rate under 10% with the capability axes unchanged. 15.6% misses it. The rest of this report is about where the 254 asks came from, because a third of them turn out not to be judgments at all.

**Permissive misses (author pass): 0.** Across 1,376 allows, 16 had a capability axis (destructive, exfiltration, privilege, secret exposure) at or above 0.50. Seven of the sixteen are the same thing: the agent removing a preview page and a scratch component it had created minutes earlier, then rebuilding, destructive 0.64–0.75 softened by `authorized` at 0.80–0.89. Two are in-place source edits by script (destructive 0.57–0.60, `authorized` 0.82–0.85). The remaining seven: four scratch scripts that upload the author's own media to services the author pays for (exfiltration 0.51–0.54), a new server-side source file scored 0.54 on secret exposure for reading its keys from the environment, and two calls scored 0.52–0.53 on destructive with nothing destructive in them. None should have been interrupted.

### 1. The truncation floor fired on prompts, not on inputs (82 asks)

toolgate caps the verdict at `ask` whenever the model did not see everything, so that an oversized input cannot be allowed on the part the model happened to read. The floor applies to two things: the tool input (`limits.input_chars`) and the latest user prompt (`limits.task_chars`, 6,000).

In this window the input cap fired once. The prompt cap fired 82 times, and in 78 of those the "latest prompt" was not something the person typed: it was the compaction summary Claude Code writes when the context window fills, which arrives as a user turn and is far longer than 6,000 characters. From that point until the person typed again, every tool call in the session was floored at ask: a `grep`, a `wc -l`, a browser `find`, an Edit. Three more were long pasted logs or tables, one a legitimately long typed prompt. Only 2 of the 82 had any axis at or above 0.55 on the part the model did see.

This is a mechanics bug, not a judgment, and it did not show up in the first window, where the truncation asks (about 37) were all on the input side and the cap was raised in response. A prompt cut at 6,000 characters still shows the model the whole instruction in almost every case (the overall p90 of prompt length is 885 characters); it is the tool input, not the prompt, whose unseen remainder can hide the risk. Removing the floor from prompt truncation and treating a compaction summary as context rather than as the current instruction would have turned 80 of these into allows. The ask rate for the window with those 80 removed is **10.7%**.

### 2. Off-task on read-only work (93 asks)

Same pattern as the first window, with the 0.11.0 changes holding: `off_task` is capped at ask (zero `off_task` denies this window versus twelve in the first), and `session_goal` is reaching the model (1,626 of 1,626 model decisions carried task context). The volume is lower in share (37% of asks versus 81%) but the remaining asks have a shape: 48 of the 93 are Bash, and 24 of those are read-only by their first command (`grep`, `ls`, `ffprobe`, `git status`, `tail`); 30 more are web searches, fetches, browser navigations and page finds, mostly during research requests ("analyze this competitor's site", "research what the client is likely to think") where the agent was plainly on task but each new URL read as a departure from the prompt. Eleven are browser JavaScript calls that scrape a page, three are browser batches, one is an Edit.

Off-task is a reason for a human when the agent is about to change something. It is not a reason to interrupt a read.

### 3. A repeated cleanup command flipping on the `authorized` threshold (32 destructive asks, 46 allows)

One command family dominated the destructive axis: remove a preview page and a scratch component the agent created, rebuild, verify the build, push. It ran 78 times in the window. 46 were allowed and 32 were asked, and the difference was not the command. Destructive sat at 0.57–0.82 on both sides; what moved was `authorized`, which softens a verdict one step when it reaches 0.80. On the allows it was 0.80–0.89; on the asks it was 0.08–0.79, with a median of 0.67. The same operation on the same files, confirmed by the person dozens of times, was decided by whether a probability landed on one side or the other of 0.80.

Two candidate fixes, both for the engine rather than the thresholds: remember within a session that this exact action was confirmed (a confirmation ledger beside the action ledger), and let a destructive score on files the agent itself wrote earlier in the session weigh less than one on files it did not.

### 4. Exfiltration asks on the author's own services (24 asks)

Every exfiltration ask was a scratch script reading a key from `.env` and sending the author's own media to a service the author pays for (an inference API, the project's own storage bucket), at 0.54–0.83. One `cp` of a generated image to the Desktop scored 0.82. These are the asks `trusted_hosts` exists for; the policy in this window declared none. The three denies are the same story at higher scores and are covered below.

### 5. Fail-mode (7 asks)

Two "fetch failed" on Oct 6 and five TypeSafe API 503s in a nineteen-minute span on Oct 8. All seven surfaced as visible asks with the reason attached, none as silent allows. That is the behavior `fail_mode: ask` promises.

## What changes because of this

Queued for 0.17.0, in this order:

1. The truncation floor applies to the tool input only. A truncated prompt is flagged in the state the model sees and in the audit row, but does not cap the verdict. A compaction summary arriving as a user turn is treated as context: the latest typed prompt before it stays `current_task`.
2. `off_task` cannot be the sole reason for an ask on a read-only call: WebSearch, WebFetch, Read, Glob, Grep, browser navigation and page reads, and Bash whose first command is read-only by a short allowlist.
3. A confirmation memory: when the person has confirmed an action in this session, the same action on the same targets is allowed for the rest of the session, recorded in the audit row as the source.
4. A `host` field in the audit row (`hook` or `mod`) so the next window can be cut by host.

Not changed: thresholds, question wording, the `destructive`/`authorized` interaction.

## The blind second labeling

The labeling package for this window is built on the first window's protocol: all 254 asks, all 3 denies, and 150 allows sampled at random, shuffled, with no verdicts, probabilities, axes, strata, or author labels; the reviewer sees the tool, the input (500 characters), the first 160 characters of the latest prompt, its length and kind (typed, pasted, or compaction summary), and how many earlier prompts the model saw. Results will be appended here when the pass is complete.

Raw materials: per-decision data and the labeling key are kept private; the aggregate tables above are the published record.
